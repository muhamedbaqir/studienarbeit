\chapter{Fault detection}
The kernel is a supervisor to all user space applications, and there is no one supervising the kernel. That is one of the reasons for splitting operating systems into user and kernel space.
When a user space application misbehaves, the kernel can easily terminate it. But the kernel is only controlled by itself. When faults happen, it cannot simply kill itself.

Just like any application, defining and reacting to exceptions is a must for achieving high resilience. A corrupted kernel that does not terminate can seriously damage the system. While it seems counter-intuitive, controlled faults and failures are essential for a resilient system.

This is why the kernel implements a variety of mechanisms to know when faults are occuring, so that it can decide how to react to them.

\section{Oops}
An Oops is simply an obeservation, that tells the kernel and its users (via logging), that a faulty operation has happened. They are one of the mechanisms to detect and communicate faults within the system. 
Oopses can have many causes, and the Linux kernel reacts differently to them based on its configuration.

Most importantly, they serve the purpose of highlighting incorrect behaviour, so that it can be debugged by the kernel developers. An oops by itself does not improve runtime resilience, but they provide a long-term debugging framework that helps developers improve the system over time.

Oopses arise from mainly two forms of exceptions:
% maybe "trigger" instead of "exceptions"
\begin{itemize}
        \item Hardware Exceptions, which happen when the CPU forbids certain operations. For example, zero division or bad instructions.
        \item Software Exceptions, which are called by kernel code. For example when a kernel module tries to access unallowed memory.
\end{itemize}

An oops is the prime example of fault tolerance: 
The kernel simply processes the fault that happens, yet continues to operate.

On a side note, the kernel is implementing a form of the fail fast resilience pattern by failing after N oopses. That pattern will be further explored in its respektive chapter.

\section{Watchdogs}
Watchdogs are processes, which monitor the behaviour of other kernel programs. Their main purpose is to detect and report that something has gone wrong, and can be configured to take further actions.

Often, watchdogs are needed in multithreading environments. When multiple processes are running as intended, but can cause issues in their interactions. For example deadlocks or thread starvation would be such issues. 

Notable watchdogs are:
\begin{itemize}
        \item Deadlock Detection: They monitor the resources and the threads, which place locks upon them.
        \item Hard Lockup Detectors: They detect when a CPU is completely unresponsive.
        \item Soft Lockup Detectors: They detect, when a CPU is running in kernel mode for too long, not scheduling other user space tasks.
\end{itemize}

\section{Sanitizers}
Sanizers are optional programs, which detect known forms of incorrect memory usage and other forms of common errors. Since they are very performance intensive, they usually remain used in debugging contexts. If the application is critical, using them in production might still be viable.

They improve resilience by detecting - at runtime - common programming mistakes and allow kernel developers to improve system reliability in the long term.

Some of the available sanizers are: 
\begin{table}[h]
    \begin{tabular}{c | p{8cm} }
        \hline
        Sanizer & Purpose\\
        \hline
        KASAN (Kernel Address Sanitizer)& Detects use-after-free and out-of-bounds errors\\
        KMSAN (Kernel Memory Sanitizer) & Detects usage of uninitialized memory \\
        KCSAN (Kernel Concurrency Sanizer) & Detects race condiditions \\
        KFENCE (Kernel Electric-Fence) & Detects heap out-of-bounds access, use-after-free and invalid free errors. Its overhead is low enough to be production viable \\
        \hline
    \end{tabular}
\end{table}

Depending on their configuration, kernel sanitizers can either log an oops or panic (i.e. terminate) the Kernel. In the scope of resilience, they provide a strong framework to detect and debug runtime errors.
